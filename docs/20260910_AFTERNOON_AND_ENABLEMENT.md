## 下午讨论的究竟是什么问题

需要分开看三件事，不能把它们都叫作“断联”。

### 1. 多设备协议和代码确实存在六项配套问题

这些问题是在源码核对与离线复现中发现的：

| 问题 | 实际影响 | 怎么解决 |
| --- | --- | --- |
| 晚安/拒绝的交互 ID 被覆盖为空 | 云端发出了意图，设备却把它当作错误轮次丢弃 | 云端保存设备确认的当前交互 ID，并用同一 ID 发送意图 |
| 云端不允许在播放态发 MIC_START | 固件本来能打断，命令却在云端被拦住 | 分开 MIC_START/MIC_STOP 的准入规则，允许合法播放打断；防止快速状态回执误取消打断命令本身 |
| 去重表满 32 项后不再接收新控制 | 连续使用后控制、甚至新唤醒会被拒绝 | 改为递增序号与固定 8 项结果缓存；淘汰结果后旧序号仍不能重执行，新轮次安全回收 |
| busy 后没有恢复路径 | 云端资源后来空出来，设备仍可能无法开始语音 | 云端按冷却时间重新接纳新输入；固件通过真实忙碌事件结束当前交互，到期从空缓冲恢复，不伪造状态版本 |
| 迟到的旧轮 MQTT 可能进入下一轮 | 旧晚安、打断或其他控制可能影响新的对话 | 增加 WSS 轮次确认，再放行该轮业务；设备执行时检查轮次、序号与有效期 |
| 只有消息投递确认，没有执行确认 | 云端不知道设备到底有没有执行，重投也没有可靠的原结果 | 增加带原 request_id 的 control_ack；重复请求返回原结果，PUBACK 不再被当作执行成功 |

这些修正的目标仍然是：多台设备连接同一个云端，各自对话、重连、打断和休眠，互不串扰。

原来修好的播放缓冲、16kHz 上行、按 SPKS 采样率下行、SPKE 排空与音频收尾、快速断线检测都保留。执行回执表示命令已应用，例如已开始本地晚安提示，**不是说扬声器已经播放完毕**。

## 为什么涉及凭证和 TLS，但没有换证书

独立凭证来自最初的多设备要求：设备不能仅凭自己填写 device_id 就取得身份，也不能让所有设备共享身份。为此，本次新增了：

- 这台设备独立的 WSS token，并在云端绑定到它的稳定设备 ID。
- 这台设备独立的 MQTT 用户名/密码。
- 云端控制程序自己的 MQTT 服务账号。

这些不是 Wi-Fi 密码。原 Wi-Fi 配置保持不变，原 API 服务配置也被保留。

WSS 原本已经使用 TLS。此次 MQTT 从明文改为 TLS，是为了让新设备账号密码在网络中以加密方式传输；新版公网认证 broker 本身也要求 TLS。**TLS 直接复用现有证书，所以不需要更换固件信任的 CA。**

已经从本机验证正式 WSS 和 MQTT 端口：证书验证成功，实际出示的证书与原证书相同。沿用的证书有效期仍到 2026-10-08，本次没有续签或延长它。

真实凭证、私有构建配置和含凭证的镜像都放在仓库外的 `D:\CodexData\JuliaPrivate\esp-28848591972c`。云端私有配置位于 `/opt/julia-runtime/control-v1-20260910`，没有把新凭证写入 Git 源码或报告。
