# 源码注释规范

文档版本：V1.0。本文规定 Julia 固件注释应如何帮助第一次阅读代码的人理解产品逻辑。返回 [项目入口](../README.md)。

## 1. 注释首先回答什么

一段有用的注释应优先回答以下问题：

1. 用户或服务器能够观察到什么行为？
2. 满足哪些条件才执行，为什么需要这些条件？
3. 成功后系统进入什么状态？
4. 失败、超时、断线或并发发生时如何收尾？

只有这些信息仍不足以定位实现时，才补充变量、任务、锁、队列或函数名称。

## 2. 使用实际含义，不复述变量名

不推荐：

```c
/* s_mic_streaming 为 true，s_dialog_listening 为 false。 */
```

推荐：

```c
/* 默认服务器唤醒模式下，待机时仍上传麦克风供服务器识别唤醒词；
 * 此时设备尚未进入“等待用户说完本轮话语”的阶段。 */
```

不推荐：

```c
/* generation 不一致时丢弃 ring。 */
```

推荐：

```c
/* 连接断开前积压的声音只属于旧连接。重新连接后必须丢弃，
 * 否则服务器会把过期话语误认为新一轮输入。 */
```

## 3. 推荐的注释层次

### 3.1 文件开头

说明模块解决的现实问题、与相邻模块的分工以及最重要的失败边界。不要在第一段堆叠内部函数调用链。

### 3.2 公共接口

说明调用者想完成的事情、调用前必须具备的条件、返回成功实际代表什么，以及失败后调用者是否需要重试。

### 3.3 分支与状态变化

解释为什么必须走这个分支。例如“控制连接断开后无法收到结束交流语义，因此当前对话必须退回待机”，比“处理 MQTT disconnect”更有帮助。

### 3.4 并发与资源归属

使用“负责连接的任务”“实际播放声音的任务”“采集麦克风的任务”等实际名称。必要时再在括号中给出函数或字段，方便搜索。

## 4. 常用内部词的通俗表达

| 内部词 | 注释中优先使用的表达 |
| --- | --- |
| busy | 本轮交流仍未完成，不能进入待机 |
| streaming | 是否正在向服务器发送麦克风声音 |
| listening | 是否正在等待用户完成本轮话语 |
| generation | 当前连接的数据归属编号，用于拒绝旧连接残留数据 |
| owner | 唯一允许操作该连接、外设或文件的任务 |
| ring | 固定容量的循环缓冲区 |
| slot | 一项已登记的联网服务或一格待处理消息空间 |
| ready bit | 对应连接、订阅或依赖已经确认可用 |
| teardown | 停止当前工作、释放资源并清除旧状态 |

代码标识符本身无需改名，但注释不能只靠这些词完成解释。

## 5. 注释不应做什么

- 不逐行翻译显而易见的赋值、判空或函数调用。
- 不把尚未实现、未测试或仅计划中的能力写成既成事实。
- 不用“显然”“简单”“正常处理”等词代替具体条件和结果。
- 不在公开注释或日志中写入密码、token、私钥、网络凭据或用户语音内容。
- 不复制协议全文；源码说明关键约束，完整报文格式链接到 [通信协议](PROTOCOL.md)。

## 6. 修改与验收

只调整注释时，运行 `scripts/verify_comments_only.py` 确认程序语句没有变化，并运行 `scripts/check_lex_balance.py` 检查块注释和多行宏。涉及行为、协议或配置变化时，还应同步更新 README、协议与验收清单，不能通过修改注释掩盖实现差异。
