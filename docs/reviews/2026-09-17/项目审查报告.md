## 一、潜在 BUG

### B1 · P1：busy 冷却恢复后，ring 与本地采集代次不一致

位置：[voice_service.c:293](D:/Espressif/projects/julia-fused-base/main/voice/voice_service.c:293)、[voice_service.c:739](D:/Espressif/projects/julia-fused-base/main/voice/voice_service.c:739)、[voice_local_capture.c:88](D:/Espressif/projects/julia-fused-base/main/voice/capture/voice_local_capture.c:88)。

当前配置同时启用了本地采集和多设备控制。收到合法 `busy / voice_capacity` 后，代码停掉 ring/pump；冷却结束调用 `voice_service_resume_uplink_after_file()`，只给 ring/pump 发放新 generation，却没有同步采集器的 epoch。采集器继续用连接建立时的旧 epoch 调用发送回调，`voice_uplink_ring_push_generation()` 拒收，随后采集器调用 `wss_transport_fail_session()`。

影响：本应在同一连接内恢复的资源忙状态，在下一次起音或继续上传时变成主动断线重连。文件传输恢复也复用此函数，但当前 SD 路径未接入，不把文件发送算作当前主要触发入口。

探针直接调用生产恢复函数、真实 capture 模块与真实 ring，输出：

```text
busy_resume: capture_epoch=10 ring_epoch=11 session_failures=1
```

建议：明确“连接代次”和“上传区间代次”的关系，由一个接口协调 ring、pump、capture 的停止/清空/恢复。如果采集代次需要变化，还必须同步能力协商及旧段失效；仅去掉 generation 校验会破坏已有的旧连接隔离保证。补上 `capture_ready → busy → cooldown → 新 capture_start/PCM2` 的集成回归。

### B2 · P1：OTA 空读等待可能约 50 分钟，注释中的 6 秒不成立

位置：[ota_engine.c:926](D:/Espressif/projects/julia-fused-base/main/ota/ota_engine.c:926)、[http_downloader.c:307](D:/Espressif/projects/julia-fused-base/main/network/http_downloader.c:307)。

两处都用 600 次空读、每次间隔 10 ms 推算“约 6 秒”。但本地配置的 HTTP 读取超时是 5000 ms；ESP-IDF 5.5.4 的 `esp_http_client_read()` 会先在 `esp_transport_read(..., client->timeout_ms)` 等待，读取超时且没有数据后返回 `-ESP_ERR_HTTP_EAGAIN`。这个等待发生在计数循环内部，不能只计算 `vTaskDelay(10)`。

触发条件：HTTP body 尚未完成，连接持续无数据，每次读取走超时返回，而不是立即返回永久错误。用虚拟时钟模拟每次读取耗时 5 秒，提取生产循环验证得到：

```text
ota_timeout: read_calls=601 elapsed_ms=3011000 failure=1
```

即 3011 秒，约 50 分 11 秒。这是受控超时场景，不是声称所有断网都会等待这么久。OTA 此时仍占用任务和 S8，影响正常交互恢复。

建议：使用“最后一次收到有效数据的单调时间”控制无进展期限，并把单次 read 的超时限制到剩余预算；永久错误直接退出。对 `EAGAIN`、不完整 EOF、慢速持续进展分别测试。两套下载循环应共用这一策略，避免只修其中一份。

### B3 · P1：显示超时后提前交还 DMA 缓冲，且刷新 API 吞掉错误

位置：[lvgl_port.c:113](D:/Espressif/projects/julia-fused-base/main/display/lvgl_port/lvgl_port.c:113)、[lvgl_port.c:132](D:/Espressif/projects/julia-fused-base/main/display/lvgl_port/lvgl_port.c:132)。

`lvgl_port_draw_bitmap_sync()` 等待完成信号超时后释放面板锁返回，没有确认 DMA 已停止；`lvgl_flush_cb()` 无论错误种类都调用 `lv_disp_flush_ready()`，通知 LVGL 复用像素缓冲。若 DMA 只是延迟完成，LVGL 重写缓冲会与正在进行的发送重叠，迟到的完成信号还可能被下一次提交误认。

此外，`s_last_flush_was_final` 只记录“是否最后一块”，没有记录绘制成功与否；`lvgl_port_refr_now_sync()` 据此返回 `ESP_OK`。即使底层立即返回错误，也会向启动动画等调用者报告成功。

提取真实 draw/flush/refr 函数，替换底层提交和信号量边界，结果：

```text
display_failure: draw=ESP_FAIL refresh_result=0 buffer_released=1
display_timeout: dma_pending=1 refresh_result=0 buffer_released=1
```

建议：分别处理“未提交成功”和“已提交但完成未知”。后者必须等待真正完成，或通过明确的驱动恢复流程确认 DMA 不再使用缓冲，再交还所有权；恢复完成前拒绝下一次提交。保存整次刷新中的第一个错误，让同步刷新 API 返回真实结果。探针证明控制流问题，未复现实机花屏。

### B4 · P2：跨任务调用 fail_session，直接写 owner 私有状态

位置：[wss_transport.c:1716](D:/Espressif/projects/julia-fused-base/main/network/wss/wss_transport.c:1716)、[voice_local_capture.c:362](D:/Espressif/projects/julia-fused-base/main/voice/capture/voice_local_capture.c:362)。

`wss_transport_fail_session()` 可由采音任务调用，却直接写普通 `bool s_session_failed`，并调用 `wss_set_owner_end_reason()` 改写 `s_session_end_reason`。WSS 任务同时读写、复位这些变量。它们既非原子，也没有统一锁；结束原因的“仅记录第一个原因”还是一次跨任务的读改写。注释声称 owner 独占和“不携带数据无需锁”，与实际调用路径不一致。

影响：存在 C 级数据竞争，故障可见性与原因优先顺序没有同步保证，重连清场边界也可能与外部写入冲突。不能用单线程主机 stub 的成功证明双核安全。

建议：外部失败统一走已有的 `wss_transport_request_session_end(WSS_TRANSPORT_END_APPLICATION_ERROR)` 请求通道，让 WSS owner 更新实际结束原因和会话状态；仅 owner 内部的发送失败可以使用内部标志。需要时给请求附上连接代次，拒绝迟到故障。
