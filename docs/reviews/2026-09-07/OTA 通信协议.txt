Native OTA 通信协议（ESP32-S3 固件远程升级）





本文档定义 JULIA 项目智能终端（Waveshare ESP32-S3-LCD-1.85（ESP32-S3R8））的固件远程升级（OTA）通信协议，规范终端与云端（MQTT Broker、策略服务器、固件服务器）之间的报文格式、交互时序与异常处理约定。协议采用双通道设计：控制面经 MQTT 长连接承载全部元数据报文（版本检查、升级判定、服务端通知、状态上报），数据面经 HTTPS 短连接承载固件二进制下载，保留 Range 请求与断点记录；当前构建的 206 恢复受响应头接口限制，不能承诺已具备可用的断点续传；所有网络连接均由终端主动建立，服务器不主动建立到终端的连接；服务器可通过已建立的 MQTT 长连接主动发布 ota_notify。
适用工程：JULIA 项目智能终端（Waveshare ESP32-S3-LCD-1.85（ESP32-S3R8））OTA 升级组件
协议基线：当前设备端实现（ESP-IDF 5.5.4）

1. 网络拓扑

1.1 网络拓扑与连接关系

本协议涉及四个网络角色，拓扑及连接关系如下：

网络拓扑与连接关系
场景说明：
终端设备（ESP32-S3R8）：运行本 OTA 升级组件，是协议交互的主动方（发起检查、下载、上报）；
MQTT Broker：控制面消息中转节点，只负责 Topic 路由与 QoS 语义，不参与任何业务判断；
策略服务器：接收版本检查请求，比对版本后返回升级判定（update=true/false）与固件清单；
固件服务器：存储固件二进制，响应 HTTPS 下载请求（支持 Range 断点续传）；
接入网：终端与云端之间的承载网络（当前实现为 Wi-Fi STA；协议对承载透明，未来可扩展至 4G 蜂窝等接入方式，需在网络接入层适配）。
场景标注（接入方式不影响协议交互）：
场景 A（当前实现与测试环境）：终端经家庭/室内 Wi-Fi AP 接入公网；
场景 B（未来可扩展的接入方式，当前未实现）：无 Wi-Fi 环境经 4G 模组 + 运营商网络接入。当前实际实现与测试均使用 Wi-Fi STA；若切换到 4G，需在网络接入层增加蜂窝模组及相应网络适配。因全部交互均由终端出站发起（MQTT 长连接 + HTTPS 短连接），运营商 NAT 不会阻塞任何报文，OTA 应用层的 MQTT/HTTPS 协议与业务交互逻辑无需因此重新设计。
连接性质：
终端 ↔ Broker：MQTT 长连接，常驻保活，承载全部元数据报文；
终端 ↔ 固件服务器：HTTPS 短连接，仅下载固件时建立，下载完成即关闭；
策略服务器通过 Broker 与终端间接交互，不直接连接终端；
部署说明：测试环境中策略服务器与固件服务器由同一台服务器（测试机）承载、Broker 独立部署；生产环境可按角色拆分部署，不影响协议交互。

1.2 终端地址标识

设备在协议中的唯一标识为 device_id（设备标识），格式为 esp- + 12 位小写十六进制字符（如 esp-aabbccddeeff）。
是什么地址：芯片基础 MAC 地址（6 字节）的十六进制表示，加 esp- 前缀；
如何获取：调用 esp_efuse_mac_get_default() 从芯片 eFuse 读取基础 MAC（出厂烧写、设备生命周期内不变），逐字节转为小写十六进制拼接而成；
是否已实现：已实现。代码位于 main/ota/ota_control_plane.c 的 native_ota_get_device_id()，所有报文的身份字段与设备专属 Topic 均基于该标识生成；
用途：作为 MQTT client_id（保证 Broker 会话唯一）、设备专属响应/通知/状态 Topic 后缀（/device/ota/{response,notify,status}/{device_id}），以及各报文中的身份字段；
稳定性：基于 eFuse 基础 MAC 而非网络接口地址，不随 Wi-Fi 重连或 IP 变化而改变。

2. 终端到服务器协议

2.1 传输层协议

承载：TCP 提供可靠传输；
安全：TLS 为 HTTPS 数据面提供加密与服务器身份校验；MQTT 控制面当前实现使用 MQTT/TCP（Broker URI 为 mqtt://，配置项 CONFIG_COMM_MQTT_BROKER_URI），未启用 TLS 加密——mqtts（TLS 加密）可通过配置切换，属于生产环境扩展选项，当前默认配置与测试环境未启用；
连接关系：MQTT 长连接和 HTTPS 固件下载连接均由终端主动建立，MQTT Broker 与 OTA 服务器分别监听并接受连接；具体 TCP/TLS 建连过程由 ESP-IDF 网络协议栈完成，本协议不展开其内部握手时序。
实现边界：TCP/TLS 的底层握手、重传等机制由 ESP-IDF 的 TCP/IP 协议栈（lwIP）与 TLS 组件（mbedTLS）负责，本 OTA 模块不自行定义传输层协议，仅通过应用层客户端接口（esp_mqtt_client / esp_http_client）使用。

2.2 应用层协议


2.2.1 MQTT 控制面：报文格式

通用规定
载荷格式：UTF-8 编码的 JSON 对象；
QoS：1；Retain：0；
字段名与枚举值区分大小写；未知字段忽略；
本文中的”长度”均指 MQTT 应用层 payload 的 UTF-8 字节数，不包含 MQTT 固定头、可变头、Topic、Packet Identifier 和设备端字符串结尾 NUL；
载荷上限：检查请求 511 B、检查响应 1024 B、服务端通知 512 B（分片重组后仍不得超过）、Topic 小于 192 B——服务器须保证响应与通知不超过上限；
“分片”指 ESP-MQTT 事件循环按原始 offset 分片投递的载荷；设备侧按 current_data_offset 写入固定缓冲重组，完整消息才追加 NUL 并解析（实现见 main/network/mqtt_comm.c）；
Topic 结构：请求用公共 Topic /device/ota/check；响应/通知/状态用设备专属 Topic <prefix>/{device_id}（如 /device/ota/response/esp-aabbccddeeff）。

服务器处理要求：
清单各字段必须完整且符合上表要求，尤其是 url 必须是有效的 HTTPS 地址、sha256 必须是完整 64 字符摘要；
服务器应保证 expires_at 给设备留出足够的下载与安装时间窗口；
响应发布到 /device/ota/response/{device_id}，QoS 1、不 retain。
校验语义说明：
有效期（expires_at）：清单是一次性任务描述，超过 expires_at 后设备不再执行该升级，防止执行已经失效或已撤回的任务；设备时间未同步（不可信）时不以此字段拒绝，但字段格式仍必须合法；
强制更新（force_update）：正常情况要求目标版本高于当前版本；force_update=true 允许同版本重装或版本回退（紧急修复场景），但它不会跳过身份、URL、摘要、镜像头和安全版本校验——强制更新只放宽版本比较，不放松其他安全约束。

error_code（错误码）取值：NONE、PRECONDITION_LOW_POWER、NETWORK_TIMEOUT、TLS_VERIFY_FAILED、HTTP_STATUS_INVALID、RANGE_MISMATCH、IMAGE_TOO_LARGE、IMAGE_HEADER_INVALID、HASH_MISMATCH、IMAGE_VALIDATE_FAILED、BOOT_SELF_TEST_FAILED、ROLLBACK_UNAVAILABLE、MANIFEST_INVALID、ARTIFACT_QUARANTINED、BOOT_PARTITION_SET_FAILED、NVS_WRITE_FAILED。
服务器处理要求：
订阅 /device/ota/status/{device_id}，按事件唯一标识（event_id）幂等去重（同一事件的重复发送不应重复计数或重复告警）；
以生命周期状态（state）驱动升级进度展示与告警，错误码（error_code）在失败/回滚/延迟场景给出原因；
当前只有 MQTT QoS 1 发布确认（PUBACK），没有云端业务级确认。

控制面就绪： T_resp、T_notify 均收到 SUBACK 后才发起 OTA 检查；断线重连后重新订阅并补查一次。
检查响应： ota_check 与 ota_check_response 经 Broker 异步转发。update=false 结束本轮检查；update=true 且清单合法时进入下载。等待窗口内非法响应触发短重试，窗口外过期/串台响应直接丢弃。

通道职责： MQTT 长连接仅承载控制元数据，HTTPS 短连接仅承载固件二进制。设备本地完成分区写入、完整性校验、启动分区切换及重启。
异常恢复： MQTT 断线、响应超时、HTTPS 中断和掉电恢复见异常时序图，详细策略见 2.2.4。

以下为断联的典型情形与复杂恢复机制，补充说明如下：
接入网络中断（信号盲区、覆盖边缘等）：设备端本地业务继续运行，镜像验收不依赖网络；按网络接入层重连策略（带上限和随机抖动的指数退避）持续重连，取得有效 IP 后恢复 MQTT/HTTPS 通信。服务端由 Broker 通过 keepalive 超时判定设备离线，等待设备重连；设备重新上线后按正常协议继续交互，服务器无需特殊处理。
终端异常掉电：设备端重启后读取 NVS 恢复记录，下载阶段会按有效断点发起 Range 恢复，但当前构建的 206 路径会因缺少响应头读取接口而失败；已完成校验但尚未提交时恢复提交流程（见下文已验证镜像的掉电恢复）；服务端不主动建立到终端的连接，设备重新上线并发起检查后按正常协议处理。
Range 断点恢复：下载中断或掉电时，部分镜像保留在目标 OTA 分区，恢复元数据按固定数据量间隔写入 NVS；后续清单与恢复记录一致时，设备发送 Range: bytes=<offset>- 从断点续传。当前 ESP-IDF 5.5.4 构建无法读取校验 206 所需的响应头，会以 RANGE_MISMATCH 终止；完成接口适配并通过 OTA-06 前，不得把该路径标为可用。断点失效或服务器不支持 Range 时回退一次全量下载；响应范围不匹配时终止传输、不提交固件，并隔离当前制品。
已验证镜像的掉电恢复：固件校验完成后先进入已验证待提交状态（READY_TO_COMMIT），再切换启动分区。设置启动分区失败或在此之前掉电时，已验证镜像与记录被保留，下一次收到同一清单时重新计算目标分区 SHA-256 并检查提交条件，通过后再次设置启动分区，无需重新下载；提交条件暂不满足（电源、资源、业务状态）时保留待提交记录并上报 deferred，条件满足后恢复提交。
新固件启动失败回滚：新固件首次启动处于待验收状态（PENDING_VERIFY），本地健康检查或固件确认失败时立即回滚（不重复验收）；确认前异常重启由 bootloader 处理未确认镜像，恢复上一有效固件，并最终上报 rolled_back；无有效旧固件可回滚时进入安全模式，等待人工处理。
