# 技术方案对比与资料检索

检索日期：2026-09-07。沿用上一轮范围，只比较固件、语音系统及相关部署选择。特点是工程取舍，不是本项目已完成的性能实测。原方案“VDA”按VAD理解；经典分段路线完整写法应为 **VAD/端点检测 → ASR → LLM → TTS**。

资料支持建议走三步：**官方文档确认能力/硬件边界 → 原作者代码确认实现/部署 → 论文与同条件实验确认效果**。以下链接均检索自官方文档、项目维护者仓库或原始论文；论文/模型宣传中的最佳指标不能直接套到本板。

## 1. 唤醒：ESP本地、服务器、其他微控制器模型

| 技术 | 主要特点 | 推荐搜索关键词 | 查找渠道 / 应取得的证据 |
| --- | --- | --- | --- |
| ESP-SR WakeNet本地唤醒 | 断网仍可检测唤醒；可在命中后才上传音频；需要持续采音和本地推理资源，换唤醒词需核对模型/定制流程 | `ESP32-S3 WakeNet benchmark custom wake word`；`ESP-SR 唤醒率 误唤醒 AEC` | 乐鑫文档/ESP-SR、ESP-SKAINET GitHub；找支持芯片、模型大小、RAM/PSRAM、帧时长、测试声学条件 |
| 服务器唤醒 | 模型更易更新、算力更宽裕；需要音频传到服务器后判断，受网络、带宽和持续上传功耗影响 | `server side keyword spotting streaming audio`；`openWakeWord false accept false reject` | 原作者GitHub、ICASSP/Interspeech论文；找流式输入要求、中文支持、误报/漏报、断网行为 |
| microWakeWord等MCU本地模型 | 可研究训练/定制小模型；需补充本工程的音频前端、推理运行时和资源适配 | `microWakeWord ESP32-S3 custom model training`；`TinyML keyword spotting quantization` | ESPHome官方文档、模型训练仓库；查中文训练数据、量化模型、推理内存和许可证 |

优先资料：[乐鑫WakeNet官方文档](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/wake_word_engine/README.html)、[乐鑫资源与识别Benchmark](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/benchmark/README.html)、[ESPHome microWakeWord](https://esphome.io/components/micro_wake_word/)、[openWakeWord原作者项目](https://github.com/dscripka/openWakeWord)。openWakeWord的Python/ONNX示例适合服务器/网关研究，不应直接认定能放到ESP32-S3。

**比较指标**：每小时误唤醒次数、漏唤醒率、命中延迟、远场/电视人声/自身播放时表现、平均电流。你方案中的方式2没有命名，可先以当前项目的服务端唤醒作比较基线。

## 2. 识别与生成：分段式、audio2audio、端侧ASR

| 技术 | 主要特点 | 推荐搜索关键词 | 查找渠道 / 应取得的证据 |
| --- | --- | --- | --- |
| VAD→ASR→LLM→TTS | 模块可替换、转写文本可检查，便于加规则/记忆/工具；阶段间有延迟和误差传递，语气信息需额外保留 | `streaming ASR LLM TTS pipeline latency`；`语音对话 首包延迟 CER RTF` | LiveKit Agents等原作者项目；查每段耗时、流式接口和取消/打断代码 |
| 原生音频/audio2audio | 直接利用音频特征，有利于语调、重叠语音和自然轮换；文本级审计、精确措辞、工具与取消控制需逐模型验证 | `speech-to-speech full duplex Moshi`；`audio language model turn taking latency` | 原始论文、模型卡、官方代码；查是否真流式/双工、输入输出并行方式及显存需求 |
| 端侧ASR→文本LLM→TTS | 可减少原始音频上云，让识别更少依赖网络；算力/内存、中文质量和功耗成为本地约束；若文本还送云LLM仍非全离线 | `sherpa-onnx streaming ASR ARM benchmark`；`Chinese ASR int8 memory RTF` | sherpa-onnx原项目、模型卡和目标板benchmark；看真实架构与资源，不能只看“embedded”字样 |

优先资料：[LiveKit Agents](https://github.com/livekit/agents)用于搭分段/实时模型对照；[Moshi论文，2024](https://arxiv.org/abs/2410.00037)及[官方实现](https://github.com/kyutai-labs/moshi)用于理解全双工音频模型；[sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)用于研究Linux/ARM等本地识别部署。

**硬件边界**：ESP-SR的[MultiNet](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/speech_command_recognition/README.html)是受支持命令集合的识别能力，不能把它当作任意句子的完整ASR。sherpa-onnx列出的ARM/Linux/Raspberry Pi等平台也不等于当前Xtensa/FreeRTOS板卡可直接运行。

**比较指标**：用户说完到第一段可听回答的P50/P95延迟、中文CER、RTF（处理耗时/音频时长）、打断后停止时间、并发资源、每分钟成本。audio2audio也可能有辅助文本通道，须看模型结构；不能仅凭名称推断“没有中间文本”或“必然更快”。

## 3. 会话交互：人工规则与语义/微状态检测

| 技术 | 主要特点 | 推荐搜索关键词 | 查找渠道 / 应取得的证据 |
| --- | --- | --- | --- |
| 固定VAD/静默超时+规则 | 实现简单、行为可解释；短等待易抢话，长等待显迟钝，难区分“嗯”与真正打断 | `VAD endpointing silence duration barge-in`；`语音端点检测 误打断` | VAD项目、语音框架文档；看最短话语、静默窗口、最长等待和误触发处理 |
| 语义/声学turn detection | 综合句意、语调或上下文判断是否说完；更适合停顿和接话，但要核对中文、计算开销和不确定性兜底 | `semantic endpointing end of turn prediction`；`backchannel detection full duplex dialogue` | Interspeech/ACL论文、LiveKit文档；查错误分布、最长等待、失败降级 |
| 个性化轮换参数 | 按用户停顿节奏调整等待时间；适应慢语速，但需要足够样本和参数上下界 | `personalized turn taking adaptive endpointing` | 对话系统论文与实现；查冷启动、用户切换、恢复默认设置 |

优先资料：[LiveKit轮换/端点检测说明](https://docs.livekit.io/agents/logic/turns/)、[自适应打断处理](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling/)。后者专门区分真正抢话与“嗯、对”等附和；功能可用性/语言效果须按具体版本和部署模式核对。

**比较指标**：抢话率、回答等待时间、错误打断率、漏打断率、长停顿后续说识别率。微状态不要只搜“情绪识别”：应拆成话语结束、附和、打断、沉默、犹豫等可观测事件。当前固件首先需要最长等待和取消协议，再做更复杂的预测。

## 4. 回答生成：原生LLM、情绪增强、记忆增强

| 技术 | 主要特点 | 推荐搜索关键词 | 查找渠道 / 应取得的证据 |
| --- | --- | --- | --- |
| LLM+近期对话上下文 | 结构简单、便于建立基线；长期偏好和跨会话事实不会自动可靠保留 | `LLM conversational context baseline evaluation` | 目标模型官方模型卡、原实现；记录prompt、上下文长度和固定测试集 |
| 情绪识别+LLM | 可将文本/语音情绪作为回答风格输入；标签可能误判，应有置信度/未知类别，不能把标签当用户真实心理事实 | `speech emotion recognition emotion2vec Chinese`；`SenseVoice SER UAR macro F1` | ACL/ICASSP/Interspeech、模型卡；看跨说话人/跨语料评测，避免同一人数据泄漏到训练和测试 |
| 记忆/RAG+情绪+LLM | 可检索偏好、历史事件或设备上下文，支持长期个性化；需处理错误记忆、过期、用户隔离、删改和检索延迟 | `conversational memory RAG forgetting user profile`；`Generative Agents memory retrieval reflection` | 原始论文、带测试的记忆实现；查检索准确性、冲突更新、忘记/删除与来源记录 |

优先资料：[SenseVoice原项目](https://github.com/FunAudioLLM/SenseVoice)研究ASR/情绪/声学事件联合输出；[emotion2vec，ACL 2024官方代码](https://github.com/ddlBoJack/emotion2vec)研究语音情绪表示；[RAG原始论文，2020](https://arxiv.org/abs/2005.11401)研究检索增强；[Generative Agents，2023](https://arxiv.org/abs/2304.03442)研究记忆、检索与反思架构。最后一篇是模拟智能体研究，不是陪伴硬件的产品有效性证明。

**如何证明新增模块有用**：固定同一LLM、测试对话和prompt预算，依次比较“基线 / +情绪 / +记忆 / 两者同时”。看事实一致性、重复询问率、错误个性化率和延迟；不要只展示几个好看的对话例子。

## 5. 环境适配与说话人/音色设置

| 技术 | 主要特点 | 推荐搜索关键词 | 查找渠道 / 应取得的证据 |
| --- | --- | --- | --- |
| 固定音量/能量门限 | 便宜、可解释；对距离、风扇、音乐、不同嗓音敏感 | `adaptive noise floor energy VAD SNR`；`底噪估计 自适应门限` | DSP论文/实现；同一录音比较误开麦、漏检与尾音截断 |
| AFE：AEC+NS+VAD | AEC抑制设备自身播放回声，NS处理噪声，VAD判断有人说话；各模块职责不同，AEC需要对齐的播放参考 | `ESP-SR AFE AEC reference channel double talk`；`Silero VAD noisy speech` | 乐鑫AFE文档、VAD原项目；查输入通道、采样率、参考延迟与双讲条件 |
| 固定TTS声线/预设 | 可重复、配置和资源管理较简单 | `TTS speaker id prosody control streaming` | 目标TTS官方API/模型卡；核对流式输出、语速/音量/情绪参数 |
| 参考音频/零样本音色 | 个性化更强；效果依赖参考音质和目标模型，增加声音资料管理与推理成本 | `CosyVoice zero shot streaming speaker similarity` | 原作者GitHub/论文/模型卡；看中文自然度、说话人相似度、首音频延迟及使用条件 |

优先资料：[ESP-SR AFE框架](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/audio_front_end/README.html)、[Silero VAD原项目](https://github.com/snakers4/silero-vad)、[CosyVoice原项目](https://github.com/QwenAudio/CosyVoice)。Silero/CosyVoice资料主要用于服务器或更强端侧平台评估，不是当前ESP32固件的即插即用组件。

还需区分三个概念：**用户是谁（声纹/用户绑定）、用户环境如何（噪声/距离）、设备用什么声音回答（TTS声线）**。它们不能用同一套“音色音量模板”替代。

## 6. 部署：本地、云端与混合

| 技术 | 主要特点 | 推荐搜索关键词 | 查找渠道 / 应取得的证据 |
| --- | --- | --- | --- |
| 本地服务器+本地模型 | 模型/数据可在局域网内管理；需要自己的CPU/GPU资源、更新与运维 | `self hosted voice assistant local ASR LLM TTS GPU` | 原项目部署文档/Docker/model card；查实际模型提供者、内存和并发配置 |
| 云端模型/服务 | 设备侧负担小，模型选择较多；依赖网络、服务限制与持续费用 | `realtime voice API concurrency latency data retention` | 供应商官方API、限额、计费及数据保留说明；用目标地区实测RTT与P95，不用宣传延迟代替 |
| 本地唤醒/控制+云端生成 | 保留本地响应和部分断网能力，同时利用云模型；两端状态、取消、版本与降级更复杂 | `hybrid edge cloud voice assistant offline fallback` | ESP32客户端与后端配套项目；追踪断网状态、消息重放、用户ID和轮次ID |

优先资料：[小智ESP32客户端](https://github.com/78/xiaozhi-esp32/blob/main/README.md)、[xiaozhi-esp32-server后端项目](https://github.com/xinnan-tech/xiaozhi-esp32-server)、[LiveKit Agents](https://github.com/livekit/agents)。用于参考模块拆分与部署方式，不意味着它们的协议与本仓库MQTT/WSS命令直接兼容。

**特别核查**：“服务器在本地”不等于“模型在本地”——本地网关也可能继续调用云ASR/LLM/TTS；数据是否外发必须沿实际请求路径确认。

## 7. 功耗：关屏在线、连接省电、深睡

| 技术 | 特点 / 与唤醒方式的关系 | 推荐搜索关键词 | 查找渠道 |
| --- | --- | --- | --- |
| 关屏但持续采音联网 | 改动较小、业务响应直接；只降低显示部分功耗，不能当深睡电流 | `ESP32-S3 I2S WiFi streaming power measurement` | 本机电流波形+IDF外设/网络文档 |
| DFS / Modem-sleep / 自动Light-sleep | 能结合空闲和连接调度省电；需检查I2S/定时任务/电源锁对可睡时间的限制和网络时延变化 | `ESP32-S3 automatic light sleep I2S PM lock DTIM` | 对应版本IDF官方文档、wifi/power_save示例 |
| Deep-sleep+外部/低功耗唤醒源 | 更多域断电；不能维持现有常规CPU/I2S/WS持续音频链，唤醒后需要恢复业务连接 | `ESP32-S3 deep sleep wakeup sources ULP audio` | 芯片数据手册、IDF sleep示例；验证实际可用唤醒源，不能假设WakeNet在深睡继续运行 |

优先资料：[ESP-IDF 5.5.4 Sleep Modes](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32s3/api-reference/system/sleep_modes.html)、[ESP32-S3系统低功耗说明](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-guides/low-power-mode/low-power-mode-soc.html)。手动进入睡眠与结合无线驱动的自动睡眠保持连接是不同场景，应按官方约束选型。

比较时固定电压、亮度、音量、AP/信号强度和工作负载，记录各状态平均/峰值电流、驻留比例、唤醒到业务ready时间及丢帧率。芯片睡眠典型值不等于带屏、功放、稳压和麦克风的整板电流。

## 8. 怎样把检索结果变成可用的方案依据

| 查找方式 | 推荐做法 | 用来回答什么 |
| --- | --- | --- |
| 官方文档 | 搜 `site:docs.espressif.com ESP32-S3 WakeNet benchmark` 等；选择本项目IDF 5.5.4及所用ESP-SR版本 | 能否运行、接口是什么、资源和硬件前提是什么 |
| GitHub | 搜原作者/组织；读README→examples→model/config→release/tag→issues中的复现；核对代码与模型各自许可 | 真正怎么实现、支持哪些平台、已知故障、能否复现 |
| 论文 | Google Scholar/Semantic Scholar发现文献，回ACL Anthology、ISCA Archive、IEEE或作者arXiv核对原文；看baseline、消融和测试集 | 为什么有效、与哪种方法比、哪些条件下优于基线 |
| 模型卡 | Hugging Face/ModelScope进入作者官方组织，查模型版本/语言/量化/训练与评测条件 | 中文支持、模型大小、推理环境、适用边界 |
| 本地验证 | 先离线统一录音回放，再固定设备实时A/B；保留版本、参数与日志 | 外部结果能否迁移到本板和目标用户场景 |

建议每个候选方案只先收集：**1份官方能力说明 + 1个可运行原项目 + 1份论文/Benchmark + 1张同条件测试表**。表中至少记录：目标硬件、模型/SDK版本、语种/噪声、P50/P95延迟、内存/CPU、电流或服务费用、已知缺点。GitHub Star数用于发现项目，不是性能或产品成熟度证明。

就当前项目而言，建议先比较“本地/服务端唤醒”和“规则/语义轮换”，用分段式管线建立可测基线，再评估audio2audio、情绪与记忆的增益。这是根据当前接口、资源与审查缺口提出的工程顺序，不是外部论文证明的唯一最优路线。
